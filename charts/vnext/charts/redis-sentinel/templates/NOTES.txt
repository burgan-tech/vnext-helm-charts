A Sentinel-aware client needs BOTH: the Sentinel password to ask who the master is, and
the Redis password to then connect to it. Tools that discover through Sentinel ask for
them in two separate fields, and giving the Sentinel password to both is the usual
mistake - it authenticates to Sentinel, discovers the master, and then fails on the
Redis connection with "please check the username or password". RedisInsight's
Auto-Discover screen shows this as a per-primary-group Password column, initially
"not assigned"; that column wants the REDIS password.

Leave any username field empty. This chart configures no ACL user, so authentication is
`requirepass` against the `default` user.

If a tool asks for a Sentinel password and then fails on the discovered database anyway,
it is forwarding the Sentinel credential to Redis rather than the one you typed. Measured
with RedisInsight's Auto-Discover: every hop works from a plain pod with the right
password, and connecting to Redis with the SENTINEL password reproduces the tool's exact
error (`WRONGPASS invalid username-password pair`). Two ways out:

  - Set both passwords to the same value. Sentinel discovery then works whatever the tool
    forwards, and failover awareness is kept - at the cost that reaching Sentinel is
    enough to authenticate to Redis.
  - Skip discovery and add the master directly, as {{ $fullname }}-0.{{ include "redis-sentinel.headlessServiceName" . }}:{{ .Values.redis.port }}
    with the Redis password. Nothing is weakened, but after a failover the connection
    points at a replica and writes return READONLY until you re-point it.

Do NOT point such a tool at the {{ $fullname }} Service for writes: it selects every pod,
master and replicas alike, so writes land on a replica at random. There is deliberately no
master-only Service - keeping one accurate would need a controller relabelling pods on
failover, which is the job Sentinel already does for clients that discover through it.

Clients should discover the master through Sentinel, not by connecting to a pod:

  redis-cli -h {{ $fullname }} -p {{ .Values.sentinel.port }} SENTINEL get-master-addr-by-name mymaster

One thing about readiness that is worth knowing rather than fixing: a pod counts as
Ready only when ALL its containers are, and the {{ $fullname }} Service publishes
the redis AND the sentinel port off the same endpoints. So a redis container that is
still loading its dataset removes that pod's SENTINEL endpoint too. During a rolling
update only one pod loads at a time, so discovery keeps working; after a full outage
every pod is NotReady at once and clients see "no sentinels reachable" rather than
-LOADING. Point Sentinel-discovery clients at the headless service
{{ $fullname }}-headless, which carries publishNotReadyAddresses.
